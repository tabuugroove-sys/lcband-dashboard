01

Как работает V1 — живой конвейер

V1 — это тот стек, который прямо сейчас зарабатывает деньги. Один Mac, ~80 launchd-агентов, единый SQLite orders.db как источник правды по CRM плюс семейство JSON-сторов (lcb_orders.json, broker_orders.json, pending_approvals.json и десятки других). Путь сообщения:

Уши realtime-gateway: TG (Telethon, 3 сессии) · VK longpoll · WA Baileys · IG Классифи- smart_funnel.classify_unified — один Opus-вызов решает «кто это, кация что хочет, какой шаг воронки» (fallback на словарь при отказе AI) Состояние orders.db (CRM) + lcb_orders.json (событие) + broker_orders.json + event graph Писари unified_dm_responder (владелец клиентских DM) · followup_orchestrator · broker pipeline · event-ops · band_member_reply — черновик всегда через Opus Контроль presend AI-review (fail-safe → skip) · tg_outbound_guard (режим live_direct) · approval-бот — только деньги/договор Отправка telegram_delivery_service — единственный процесс с правом писать в TG-аккаунт · wa_auto_sender · VK API — анти-бан лимиты, jitter Аудит morning-reconciliation · watchdogs · SLA-надзор · daily report

Сильная сторона: полное покрытие бизнеса. Два года инцидентов превращены в правила: анти-бан, запрет писать музыкантам, hard-block на финансы, refusal-политика, brand-guard, каноны цен. Всё это живёт в V1 и нигде больше.

Структурная болезнь (полный разбор 11.07, 51 агент-картограф): из 25 подтверждённых конфликтов 17 — один и тот же класс дефекта: общий JSON-файл, куда пишут несколько процессов без единого владельца и без общей блокировки. Отсюда реально случавшиеся double-send через pending_approvals.json (~12 писателей, 4 режима блокировок), гонки WA-очереди (6 писателей), dead-letter-очередь, терявшая ответы клиентам, риск повторного питча из-за sent_proposals без lock. Плюс: ~350 env-флагов без приоритетов, логика воронки размазана по 4 местам, нет канонического времени, нет correlation-id. Лечится это не заплатками, а принципом «у каждой единицы состояния один сервис-владелец» — что и есть V2.

02

Как работает V2 — Core

Core V2 — транзакционное ядро в rewrite/, построенное по нормативным документам (MASTER_PLAN.md v5.5, DOMAIN_MODEL.md). Четыре принципа, каждый из которых закрывает класс болезней V1:

  • Один писатель БД. Только ядро открывает core.db на запись; все изменения — типизированные команды через CommandBus, история append-only, ревизии неизменяемы. Гонка «12 писателей в один JSON» структурно невозможна.
  • Durable inbox/outbox. Входящее подтверждается провайдеру только после записи в ядро; исходящее — это intent → attempt → receipt, «поставлено в очередь» ≠ «отправлено».
  • Shadow запрещает все внешние эффекты, не только отправку: календарь, папки, контакты, файлы. Обойти executor из shadow-кода нельзя по построению.
  • AI не пишет состояние. Модель выдаёт типизированный intent; проверка, мутация и эффект принадлежат ядру.

Что V2 уже умеет

  • Видит 100% входящих TG и WA (зеркало, когорта «все») + вся история импортирована (85 739 сообщений).
  • Пишет черновики ответов, разбуженный входящим за секунды (nudge), а не по таймеру.
  • Ручная отправка оператором из V2-приложения (TG и WA) — через legacy-очередь, с провайдерским receipt.
  • Проекция воронки: стадия из головной ревизии opportunity, бейдж V2/V1 в папках приложения.
  • Первый разрешённый write в legacy: прямые лиды ядра → orders.db → TG-папки (14.08, живой).
  • Operations-мост: ~70 операторских действий legacy доступны из V2-приложения по allowlist.

Чего V2 не делает

  • Не отправляет сам. agent_send_enabled=false, блокеры: «диспетчер агента не развёрнут» + транспорт TG в режиме live_direct у V1. При этом в UI автономия уже выбрана (24.07) — намерение есть, исполнителя нет.
  • Не владеет входящими. Режим mirror: копия идёт в ядро, обрабатывает по-прежнему V1.
  • Не ведёт воронку — 1 opportunity; стадии читает из legacy CRM.
  • VK/IG живьём в ядро не пишутся (только исторический импорт).
  • Проекции наружу (календарь Google, папки, контакты) — выключены до отдельных canary.
03

Мосты между пайплайнами

Системы связаны девятью явными мостами. Направление важно: почти всё течёт из legacy в ядро (наблюдение), и только два узких канала — обратно (и оба под гейтами).

Post-result shadowlegacy → coreРешение V1 по сообщению (включая «промолчал») записывается в ядро — это «левая сторона» сравнения

Канон двух пайплайнов (с 19.07): отправляет только legacy, Core — в тени; любое изменение поведения — сначала сценарий и инвариант, несрочное строится только в Core; срочное — «Core решает, legacy исполняет» с временным фиксом и условием снятия. Проверяется машинно: ledger-запись без «Dual pipeline package» не проходит валидацию.

05

Как выбирается «лучшая архитектура»

Важная рамка: выбор «V1 или V2» как целого уже сделан — решением от 10–11.07 цель зафиксирована (эволюция внутри, strangler-миграция, V2 — целевой хребет). Реальный открытый вопрос другой: когда каждый конкретный кусок работы можно безопасно передать ядру. И для этого построен измерительный конвейер, а не спор мнений:

  1. Shadow-сравнение решений. Одно и то же входящее проходит оба мозга. Решение V1 нормализуется, ядро независимо строит своё; сравнение идёт по шести осям: отношение к контакту, намерение, действие, предмет, деньги/договор, внешний эффект.
  2. Арбитраж = ground truth. Расхождения попадают во вкладку «Арбитраж» (основное приложение → LCB 2.0); твой вердикт по каждому — и есть критерий, кто прав. Не «V1 всегда эталон»: в 106 задокументированных случаях V1 ошибался.
  3. Бенчи писаря. На корпусе из 8 реальных переписок: V1 отправил все 8; V2 дал 5 черновиков и 3 честно отправил оператору, 0 ошибок. Два прогона различались только стилем текста — поведение стабильно.
  4. Измеримый cutover-гейт (для каждого канала/назначения): тень ≥14 дней и ≥300 событий; расхождений по деньгам/договорам — ноль; прочих <2% и все разобраны; откат отрепетирован и укладывается в 15 минут.
  5. План волн (аудит 01.08: 49 агентов, 112 возможностей V1, 33 подтверждённых пробела, 31 блокирует cutover): W0 сравнение → W1 «руки» (отправка+гейты) → W2 цена → W3 память сделки → W4 дожимы (первая безопасная миграция) → W5 брокер → W6 лиды из event-чатов → W7 событие.

Где этот конвейер на момент среза: стоит на нуле. 175 сравнений накоплено, все — blocker (154) или mismatch (21), совпадений ноль, судейских вердиктов ноль, последнее сравнение — 12.08. Причина не в расхождении движков, а в инфраструктуре: интерпретатору не достались AI-провайдеры (vault заблокирован, суточные бюджеты CLI исчерпаны), поэтому большинство сравнений падает как «нет принятой интерпретации». Воронка это подтверждает: из 49 LCB-тредов все 49 показывают бейдж V1 — в ядре ровно одна сделка. Данных для выбора пока нет — это и есть волна W0.

06

Что было сломано на момент среза

Битый venv → 3 агента лежат

12.08 ~16:20 brew cleanup удалил Python 3.14.4, на который указывал симлинк .venv/bin/python. Три plist'а V2 с этим путём (shadow-writer, calendar-mirror, tg-live-comparison) с тех пор умирают с кодом 78, не успев записать ни строчки. Писарь выживает только потому, что листенер будит его напрямую. Лечение — пересоздать venv или перевести plist'ы на /opt/homebrew/bin/python3 (как уже сделано у core-app-backend).

telegram-delivery в crash-loop

Preflight отказывается стартовать: 5 критических файлов (event_ops_bot, project_reviewed_send, send_pending_approval, telegram_delivery_queue, telegram_delivery_service) изменены и не закоммичены (правки от 13.08, 19:23). Это единственный владелец отправки в TG: пока он стоит, исходящие стоят и у V1, и у V2; 5 команд за 14.08 уже протухли (expired) и потребуют переотправки.

Offsite-реплика молчит 6 дней

Последняя успешная синхронизация capytime-реплики — 08.08; с тех пор SSH до сервера таймаутит, а уведомления об этом гасятся дедупликацией — отказ тихий.

07

Вывод

V1 — работающий, полный по покрытию, но структурно больной конвейер: его дефекты — один класс (общее состояние без владельца), и чинить их внутри V1 бессмысленно. V2 — архитектурно правильный ответ ровно на эту болезнь, он уже видит весь трафик, держит всю историю и пишет черновики, но пока не умеет главного — «рук» (отправки) и воронки, и по канону не получит их без данных сравнения.

Поэтому «выбрать лучшую архитектуру» сегодня — значит не сравнивать схемы на бумаге, а запустить измерение: починить runtime (venv, delivery), разблокировать AI-провайдеров интерпретатора и начать судить арбитраж. Как только сравнение начнёт производить вердикты, выбор по каждой волне (дожимы → брокер → лиды → событие) станет арифметикой гейта: 14 дней, 300 событий, ноль расхождений по деньгам.
