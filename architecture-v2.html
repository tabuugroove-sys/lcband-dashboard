🧬 Architecture v2 — proposal

DRAFT Параллельная архитектура классификации и маршрутизации лидов. Старый ai_classify_chain.py остаётся в production до cutover. Источник: обсуждение 13.05.2026.

TL;DR

  • Один L1 (Gemini Flash Lite) c богатой structured-schema решает факты о посте, не маршрут.
  • Маршрутизация — Python-роутер на (verdict, geo, budget, signals), не LLM.
  • L2 (GPT-5.5) — арбитр только для unsure / конфликтных кейсов.
  • Два domain-агента на Opus: LCB Sales и Broker. Тред принадлежит агенту с момента первого касания.
  • Approval-bot — только для платежей и составных бюджетов выше cap. Всё остальное — auto.
  • Все исходящие (любой агент, любой канал) проходят через единый outbound_policy: sanitize → ai_review → governor → channel. См. §5a.

2. L1 contract — JSON schema

L1 возвращает факты, а не решение. Роутер собирает route в коде.

{
  "lcb_match": true,            // подходит ли под LC Band / drum / solo
  "lcb_type": "cover_band" | "drum_show" | "solo_musician" | null,

  "broker_match": true,         // есть ли тип подрядчика в нашем пуле
  "broker_categories": ["host", "dj", "sound", "dance", "show", ...],

  "event_signals": ["date", "city", "budget", "guests"],
  "geo": "moscow" | "spb" | "regions" | "abroad" | "unknown",
  "budget_hint": "low" | "normal" | "premium" | "unknown",

  "lcb_confidence":    0.0..1.0,
  "broker_confidence": 0.0..1.0,
  "intent_confidence": 0.0..1.0,   // вообще ли это запрос на услугу

  "is_refusal": false,             // hard refusal regex matched before L1
  "is_musician_promo": false       // самопромо коллег — никогда не отвечать
}

Confidence — per-field, не глобальный. Эскалация в L2 — если любой из релевантных *_confidence ниже порога (по умолчанию 0.7).

3a. Router-as-contract

Ключевое уточнение: v2 не переписывает агентов, а вводит единый контракт между ними.

Остаются как есть: tg_realtime_monitor, tg_responder, broker_*, payment_event_handler, agent_watchdog, dashboard_backend. Меняется только центральная прослойка:

входящий пост/DM
  → L1 structured triage   (ai_triage_v2.classify_v2)
  → deterministic router   (ai_triage_v2.route_v2)
  → owner/thread state     (thread_state.lock_thread)
  → task для нужного агента (agent_tasks)

Поведенческое правило для каждого агента

from thread_state import is_my_thread

mine, reason = is_my_thread("lcb", thread_id)   # или "broker"
if not mine:
    return   # молча выходим, без Opus, без классификации

После этого:

  • tg_responder не лезет в broker-заказы (owner=broker → выход).
  • Broker не пишет директору/подрядчику без sanitized brief — берёт payload из agent_tasks, не из переписки клиента.
  • owner=both → две задачи: LCB pitch клиенту + Broker по доп. подрядчикам.
  • owner=skip → downstream не тратит Sonnet/Opus.

Самая большая экономия v2 — не от новых агентов, а от того, что старые перестанут принимать route-решения каждый по-своему.

4. Thread ownership & state

Правило

  • Тред принадлежит агенту с момента первого касания (owner_agent ∈ {lcb, broker, both}).
  • Новые сообщения в существующем треде НЕ идут через L1 — сразу владельцу.
  • L1 включается только когда thread_id отсутствует в lead_threads.
  • Exception: явный новый intent внутри треда («а ещё нужен DJ») → owner делает handoff, не L1.

DDL — новые таблицы в orders.db

CREATE TABLE lead_threads (
  thread_id              TEXT PRIMARY KEY,   -- "tg:@username" | "vk:peer_id"
  channel                TEXT NOT NULL,      -- tg | vk
  owner_agent            TEXT NOT NULL,      -- lcb | broker | both | skip | manual
  status                 TEXT NOT NULL,      -- active | hold | closed
  first_seen_at          INTEGER NOT NULL,
  last_inbound_at        INTEGER,
  l1_verdict_json        TEXT,               -- замороженный L1 первого касания
  order_id               INTEGER REFERENCES orders(id),
  route                  TEXT,               -- lcb_direct|broker_order|hybrid|drum_brief|skip|manual_review|lcb_lowcost_skip
  route_reason           TEXT,
  lcb_type               TEXT,               -- cover_band|drum_show|solo_musician|null
  broker_categories_json TEXT,               -- ["host","dj","sound"]
  route_locked_at        INTEGER             -- наличие = "не пере-роутить"
);

CREATE TABLE agent_tasks (
  task_id        INTEGER PRIMARY KEY AUTOINCREMENT,
  parent_thread_id TEXT REFERENCES lead_threads(thread_id),
  from_agent     TEXT NOT NULL,           -- lcb | broker | router
  to_agent       TEXT NOT NULL,
  payload_json   TEXT NOT NULL,           -- {need, date, city, budget_cap, ...}
  status         TEXT NOT NULL,           -- pending | in_progress | resolved | failed
  resolution_json TEXT,                   -- {candidates, prices, ...}
  requires_user_approval INTEGER DEFAULT 0,
  created_at     INTEGER NOT NULL,
  resolved_at    INTEGER
);

5. Handoff протокол LCB ↔ Broker

Пример: клиент написал «нужна кавер-группа + DJ + ведущий на 14 июня в Москве, бюджет 500к».

  1. L1 → lcb_match=true, broker_match=true, broker_categories=["dj","host"].
  2. Router → route=hybrid, owner=lcb.
  3. LCB Sales создаёт agent_tasks {to: broker, need: ["dj","host"], date, city, budget_cap: 200000}, свой draft в hold.
  4. Broker берёт задачу, ищет в broker_vendor_roster.json 2-3 кандидата на каждую категорию, считает суммарный бюджет.
  5. Если суммарно ≤ budget_cap → status=resolved, requires_user_approval=0. LCB Sales добавляет блок «доп. услуги» в draft, шлёт клиенту.
  6. Если > cap или конфликт цен → requires_user_approval=1, approval bot тебе. Решение → LCB Sales продолжает.

Никаких прямых in-memory вызовов между Python-агентами. Только через DB — переживает рестарт launchd, аудируется, есть метрика «сколько часов задача висит».

5a. Universal outbound gate — все исходящие через AI review

Параллель к router-as-contract на входе: на выходе один общий chokepoint. ЛЮБОЕ исходящее сообщение в любой канал (TG event/DM, VK community/DM, IG DM, approval-bot draft) проходит через outbound_policy(). Никаких прямых send_message() в коде агентов.

Сейчас ai_review_before_send гейтит только client-facing (tg_responder, telegram_monitor). contractor_relay_agent, broker_contractor_followup_agent, drum-brief к Вадиму, VK-ответы — обходят review и governor. Поэтому проходят hardcoded templates и потенциальные утечки t.me/{client} подрядчикам.

Три категории получателей

В v2 ровно три типа адресатов, всё остальное либо подвид, либо канал доставки:

recipient_type Кто Sanitize Review profile
lcb_internal Свои: Вадим, Ира, Стас, LAZ, Лео, чат-вокалисты, band-чат события минимум рабочий контекст, без лишней воды; бюджет/контакты только если этому чату реально разрешено
contractor Внешние подрядчики/музыканты — host, DJ, звук, танцы, фото/видео, разовые «коллеги» режем client @handles, телефоны, profile URLs, имя source-чата, бюджет клиента можно просить видео/цену/условия; нельзя сливать клиента, источник, бюджет клиента
client Клиенты/организаторы — DM-лиды, event-чаты, VK community, IG no-op (логируем длину, ссылки, цифры) полный ai_review_before_send: цены, факты, тон, no contractor contacts

Вадим — это lcb_internal, не contractor. Он директор Noize Drum, наш постоянный партнёр — рабочий контекст ему передавать можно (формат события, дата, длительность, наш предложенный клиенту бюджет). Чужие подрядчики/музыканты, с которыми broker ведёт разовые сделки → contractor. Граница простая: «свой» = тот, кому мы доверяем видеть нашу экономику конкретной заявки.

Approval-bot — это delivery mode, не получатель. Draft, который уходит Михаилу в bot, относится к одному из трёх типов (например draft питча клиенту) и проходит gate ПОД этим типом. Михаил видит уже sanitized + reviewed текст. После approval тот же draft уходит реальному получателю без повторного review (кэш по hash).

Контракт вызова — один gateway

from outbound_policy import send_outbound

await send_outbound(
    channel="tg",                    # tg | vk | ig
    recipient_role="lcb_internal",   # ОБЯЗАТЕЛЬНО — client | contractor | lcb_internal
    purpose="drum_city_ask_status",  # audit-tag в session_actions
    recipient="@vadimnoize",
    text=draft,
    context=context,
)

Policy выбирается только по recipient_role — никакой эвристики по тексту (if "drum" in text…), никакого регекса по username. Если роль не передана → RoleRequiredError, gateway не отправляет. Fail-closed.

Известные дыры в текущем коде

  • contractor_relay_agent.py:168 — tg_client.send_message(vadim_entity, text) мимо ai_review и governor'а.
  • send_pending_approval.py:348 — буквально печатает "AI-review skipped: contractor-side broker message". Не «review не пропустил», а обход вручную.
  • broker_contractor_followup_agent.py:267 — то же, прямой send_message подрядчику.

Все эти call-site'ы переключаются на send_outbound(...). Старые «специальные» байпассы удаляются — gateway либо пропускает, либо нет, исключений «для подрядчиков скипнем» больше не бывает.

Правила

  • Запрет прямых send_message в бизнес-коде. CI-lint: grep send_message вне outbound_policy.py и channel_adapters/* → fail.
  • recipient_role обязательный, без угадывания. Только client | contractor | lcb_internal. Любой новый «специальный» получатель сначала укладывается в одну из трёх категорий — не добавляется новый role.
  • Hardcoded outbound запрещён. Текст либо approved через approval-bot, либо сгенерён Opus и проверен ai_review здесь же. Никаких f-string шаблонов в коде агентов.
  • Sanitize deterministic ДО ai_review. Defense in depth — даже если Opus сольёт @username, regex уберёт.
  • ai_review — вторая линия. Ловит семантику, которую regex не возьмёт («Вадим, клиент Иван 38 лет на дочкину свадьбу» — sanitize пропустит, review должен сфлагнуть лишние детали).
  • Fail-safe = skip. Любая ошибка (Sonnet timeout, sanitize crash) → НЕ слать. Тишина > утечка.

Cutover

  1. Написать outbound_policy.py + sanitize.py + contractor profile в ai_review.
  2. Переключить contractor_relay_agent и broker_contractor_followup_agent (самые горящие — сейчас bypass).
  3. tg_responder и telegram_monitor — обернуть существующий ai_review_before_send в общий gate.
  4. VK responder, IG responder.
  5. CI-guard: send_message вне gate/adapters = fail build.

6. Outbound governor (shared rate-limiter)

Вытащить anti-ban из tg_responder.py и vk_auto_responder.py в общий outbound_governor.py.

ChannelLimit/dayJitterCooldown trigger
TG (LCB account)4015–35sPeerFlood → 24h
VK (Kate token)2030–60sCAPTCHA → 6h + alert

Broker и LCB Sales пишут в общую очередь — governor решает порядок и паузы. Иначе LCB-агент выжжет TG-квоту на питчах, Broker про это не узнает, словит PeerFlood, бан.

7. Approval gates

Требуют твоего OK

  • Любое исходящее, касающееся оплаты / предоплаты / договора / реквизитов.
  • Составной запрос, где Broker подобрал вариант выше budget_cap.
  • Конфликт цен между подрядчиками одной категории (нет однозначного выбора).

Auto-send (с pre-send AI review fail-safe)

  • Холодные питчи LCB Sales (правила те же, что сейчас: молчание ≥2 дня + ai_review_before_send=ok).
  • Broker outreach подрядчикам из roster (B2B, не клиенты).
  • Clarifier-вопросы клиенту, follow-up'ы по существующим правилам.

8. Trash audit

Trash — не «удалить и забыть». Все skip/trash логируются с reason в trash.jsonl.

Раз в неделю Gemini Flash Lite пробегает 100 случайных постов из trash с вопросом «не лид ли это?». Флагнутые → тебе в bot одним батчем. Расход — копейки. Это страховка от тихих регрессий L1, чтобы не терять деньги вслепую.

9. Pool правды о подрядчиках

Уже существует:

  • broker_vendor_roster.json — структурированный реестр.
  • tg_contact_roles.json — большая выгрузка ролей из всех переписок.

10a. A/B canary procedure — честное сравнение v1 vs v2

Shadow-run из §10 step 3 даёт картину «что v2 решил бы», но не «какая реальная конверсия у v2». Для второго нужен canary — малая доля реального трафика, которую v2 ведёт от начала и до отправки. Отправляет всегда только один pipeline на один лид, иначе дубли и бан-риск.

Пять правил, без которых canary не работает

  1. Ключ хэширования — thread_id, не order_id. Order появляется не на первом касании; thread_id (из thread_state.make_thread_id(channel, peer)) стабилен с момента первого touch. Один лид всю жизнь в одном pipeline. 
    def choose_pipeline(thread_id: str, pct: int) -> str:
    h = int(hashlib.sha1(thread_id.encode()).hexdigest(), 16) % 100
    return "v2" if h < pct else "v1"
  2. Не процент от трафика — per-purpose whitelist. 10% случайно даёт 10% payment-сообщений тоже. Это плохо. Конфиг: 
    {
  "pipeline_v2_canary": {
    "ingest_post_classify":    10,
    "cold_outreach_first":      5,
    "payment_intent_classify":  0,
    "outbound_promise":         0,
    "refusal_handling":         0
  }
}
    payment_* / refusal / urgent остаются на v1 пока каждый purpose явно не прокляйнен.
  3. pipeline_version через contextvars, не через аргументы. Прокидывать тег через каждый AI/send вызов = десятки правок, легко забыть. Лучше один contextvar, который router устанавливает раз, а все logger'ы читают. 
    import contextvars
PIPELINE_VERSION = contextvars.ContextVar("pipeline_version", default="v1")

# в ai_usage_tracker / message_event_log / session_actions:
entry["pipeline_version"] = PIPELINE_VERSION.get()
  4. Circuit breaker — обязателен с первого дня. Watchdog читает ai_timeline.jsonl каждую минуту, считает v2 error/skip rate за 15 минут. Threshold пробит → автоматически пишет нули в runtime_config.pipeline_v2_canary и алертит в commander-bot. Иначе бажный v2 8 часов до утра тихо теряет лиды.
  5. Дашборд-тайл ДО canary, не после. Метрики «v1 vs v2: AI calls/sent, tokens/sent, skip rate, stage changes» должны быть живые ещё на shadow-фазе. Иначе флипнул 5% и сидишь без чисел первые часы. Тайл строится параллельно с shadow-прогоном.

Чего НЕ делать

  • Не переиспользовать LCBAND_L1_SHADOW_MODE. Тот флаг — про L1 commit внутри ai_classify_chain. Pipeline canary — другой уровень. Отдельный config-ключ, иначе путаница «что shadow, что canary».
  • Не включать canary до закрытия bypass'ов из §5a. v2 шлёт через outbound_policy, v1 шлёт мимо — сравнение некорректное, мы измеряем не pipeline'ы, а наличие gate. Сначала close bypasses (contractor_relay, send_pending_approval, broker_followup), потом canary.
  • Не ставить canary > 20% пока хотя бы 7 дней не прошло без circuit-breaker срабатываний.

Порядок шагов (после §10 step 1-2)

  1. A Закрыть bypass'ы из §5a (outbound_policy, sanitize, 3 роли).
  2. B Добавить PIPELINE_VERSION contextvar + read в logger'ах.
  3. C Дашборд-тайл pipeline-ab (живой на shadow).
