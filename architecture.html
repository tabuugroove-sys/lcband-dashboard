Ingress и routing

Launchd держит входящие каналы и отдаёт события ответственным владельцам.

  • com.lcband.realtime-gateway supervises TG realtime, payment listener и VK longpoll.
  • tg_realtime_monitor.py ловит TG event-чаты/private DM, обновляет context card и зовёт LCB writer.
  • vk_longpoll_listener.py триггерит vk_auto_responder.py; WA идёт через native Desktop queue.
→

Owners и state

Смысловая работа разделена по владельцам, чтобы не было двух writer'ов на один диалог.

  • unified_dm_responder.py владеет LCB direct DM: intake, sales, contract, production, content.
  • broker_dialog_agent.py и broker_casting.py владеют broker events, contractors, media и relay.
  • lcb_orders.json, broker_orders.json, orders.db.message_events остаются source-of-truth слоями.

  1. Listener ловит событие
    NewMessage(incoming=True, is_private=True) → запускает тред. Работает на любой новый private DM, не только первое сообщение.
  2. Входящее фиксируется в cache, потом обновляется картотека force=True
    _record_incoming_to_cache(out=False) → lead_context_enricher.enrich(username, "tg", force=True). Enricher обходит 30-мин freshness check, читает orders.db.message_events через unified_message_store; legacy cache fallback включается только явно. Один AI pass возвращает context-card, active event, follow-up, funnel_stage и event_threads для команды по той же дате; funnel_stage_classifier.py только применяет этот verdict к orders.db без второго AI-запроса. Если клиент ответил хотя бы один раз, минимальная context-card сохраняется до AI. Если known events пустой, но thread явно про одно мероприятие, создаёт event через event_graph.py в orders.db.eg_* и переносит key asks в event-card.
  3. Запуск агента
    unified_dm_responder.handle({channel, username, text, ts})
  4. LCB band-member route
    LAZ/Ира/Стас/Лео/Teddy из tg_whitelist.json идут в band_member_reply.py: только факты по подтверждённым event'ам, performer-safe репертуар и runtime-поиск конкретных файлов в promo-папке; payment/new-gig/personal → silent.
  5. LCB promo material resolver
    lcb_promo_materials.py раскрывает promo-папку Я.Диска и даёт writer'у отдельные ссылки по смыслу запроса: видео, фото/костюмы, райдер/репертуар, LAZ/TEDDY; общая promo-ссылка остаётся fallback.
  6. Агент читает свежую карточку
    get_or_enrich(username, channel) — если карточка устарела (cron-путь) — обновляет; иначе берёт актуальную из кеша. До classify собирается Context-hint: роль текущего контакта, active event, stage, writer mode, waiting flags и next action.
  7. Classifier с context-hint
    Opus-classifier получает переписку + structured context. Он не должен повышать контакт до event_organizer_active, если текущая роль из lcb_event_context.py/event_context_events — performer/vendor/tech. Post-classify role normalization остаётся safety net перед writer.
  8. Opus генерирует ответ
    Полный контекст переписки + карточка + текущий текст → claude_cli.call_opus()
    API fallback отключён для переписки/follow-up/context/classify: если CLI недоступен, writer stop/skip; API остаётся только для первичного pitch.
    Anti-ban: 8/run · 40/день · jitter 15–35s
  9. Routing verdict
    sent → TG/VK direct send; WA → funnel_maintenance.py queues wa_computer_use_queue.json for WhatsApp Desktop path even before active window · money → notify bot only · skipped → spam/refusal/musician/unclear · error → log/state consultant gap; no second DM sender
  10. Dual-stream после отправки одновременно
    Поток 1 → сообщение отправлено в DM
    Поток 2 → _record_outgoing_to_cache(out=True) + enrich(force=True) — исходящий текст тоже попадает в картотеку и активный event
