Как сейчас работает LCB automation

Карта текущей реализации: realtime и scheduled процессы приносят события, state сходится в orders.db и read-model'ы, LCB client text пишет один writer, а broker-переписки уводятся в отдельный broker state до LCB writer.

Обратная запись после output: successful send / mark-sent → outbound_recorder.record_outbound(namespace="lcb") → orders.db.message_events → context refresh/promises. Память переписок
Канонически вся переписка должна сходиться в один raw-log: orders.db.message_events. Канальные файлы вроде conversation_cache/, vk_conversation_cache/, wa_cache/, ig_conversation_cache/ могут оставаться cache/export зеркалами, но это не четыре независимых памяти. one memory layer
Ответ музыканта → состав event'а

Это не ручная правка карточки. Ответ музыканта сначала сохраняется как raw-message, потом общий context owner превращает переписку в event_threads, а event-ops читает уже этот SSoT и решает, кто confirmed / negotiating / pending / unavailable.

1. TG private DM

Музыкант отвечает в личке: «могу», «не могу», «поставь за мной», «уточню», присылает репертуар или задаёт вопрос по дате.

→

2. realtime owner

tg_realtime_monitor.py ловит входящее через tg_session_monitor.session и передаёт в DM pipeline. Outgoing/manual replies также попадают в тот же лог.

→

3. raw message SSoT

message_event_log.py пишет событие в orders.db.message_events. Это canonical история переписки; JSON/cache слои не являются источником отправки или статуса.

4. hard route

unified_dm_responder.py проверяет lcb_roster.py, tg_contact_roles.json и operational performer entries в tg_whitelist.json. Роли lcb_musician, resident_*, recruited performers и coordination-candidates уходят в band_member_reply.py, а не в client writer.

→

5. context extraction

lead_context_enricher.py читает orders.db.message_events, собирает командные треды вокруг конкретной даты и пишет event_threads: availability, thread_status, thread_summary, last_message_ts.

→

6. event SSoT

lcb_orders.refresh_contact() материализует обновлённый event-card в lcb_orders.json. Для production это главный read-model: дата, формат, organizer, participants, event_threads, coordination_requests. Контрактные факты для календаря сверяются со свежей перепиской в orders.db.message_events: выбранная цена/состав после финального подтверждения перекрывает старые CRM и event-context варианты. Event identity держится на клиентском order/client signal + date: performer-availability и casting-side оболочки lcb_orders.dedup_now() сливает в единственную реальную карточку этой даты, а неоднозначные даты не склеивает.

7. lineup resolve

event_ops_bot.resolve_production_lineup() читает lcb_orders.json.event_threads + свежие recruit-диалоги из orders.db.message_events, плюс client-side thread организатора для проданного состава. Он не верит сырой карточке event_planning.json. Если у события есть TG-группа, event_ops_logistics_agent сначала синкает актуальное членство группы в tg_group_lineup_cache.json; stale group ids без production-card пропускаются, чтобы не блокировать refresh остальных карточек. Резолвер не считает silence подтверждением и поднимает незакрытые альтернативы состава как open_decision. Для brand=noize_drum / service_type=drum_show performer assignment принадлежит broker/Noize director: event-ops не запускает LCB lineup resolve, group-add или drum/bass/sax recruit.

→

8. operational cache

event_ops_state.json хранит только рабочие решения: lineup_resolve cache, musician_availability, drummer_recruited, bass_recruited, sax_recruited, *_declined, pending approvals и привязку вручную созданных TG-групп через event_ops_bot discover-group. Это не raw-message SSoT.

→

9. visible surfaces

events.html, briefing, band-chat approval и repertoire должны показывать один resolved lineup: confirmed, negotiating/pending, unavailable и gaps. Negotiating отображается как участник состава под вопросом, не как confirmed.

Что обновляется сразу

orders.db.message_events получает входящее сообщение. Это единственное место, где доказывается сам факт ответа музыканта.

Что обновляется после context refresh

lead_context_store.json как legacy mirror, orders.db contact_context/event_context и lcb_orders.json.event_threads.

Что обновляет event-ops

event_ops_state.json хранит кэш решений и статусы рекрутинга, чтобы не спрашивать одного и того же музыканта повторно. Direct confirmed-brief разрешён только по approved plan_participants / group participants, не по сырому lcb_orders.participants. Перед новым group/recruit/materials proposal cleanup_event_ops_pending_approvals() истекает stale approval-кнопки: past/missing event doc, unknown, superseded noanchor, stale group-add и пустые/неподтверждённые source-message материалы. За день до события с явным IEM/in-ear в карточке event-ops один раз напоминает TG-группе артистов взять проводные наушники. Точечные operator-directed сообщения в уже созданную event-группу идут через event_ops_bot operator-group-message, а короткие вопросы организатору через event_ops_bot operator-organizer-message; платежные формулировки требуют явный --allow-finance и логируются в event_ops_log.jsonl / message_events. Выбранные клиентом репертуар/костюмы event-ops берёт из orders.db.message_events и отправляет в TG-группу без approval как узкое исключение event_group_client_materials: caption собирается finance-free из lcb_orders, source msg_id клиента пересылаются следом, затем агент пишет отчёт в commander/notify bot. Дедуп этого auto-send не зависит от свежего текста карточки: стабильный ключ строится по event_id + organizer + source_message_ids, а send-time guard дополнительно сверяет уже отправленные event_ops_group_client_materials в orders.db.message_events, чтобы уточнение caption не породило повтор в группе. После rider-ready сигнала режим sync_event_media_capture_requests() один раз закрывает live-video capture: если известен видеограф, пишет ему; иначе организатору — просит договориться, чтобы видеограф поснимал выступление LCB, и фиксирует как потом забрать исходники/ссылку для монтажа. В той же цепочке sound contact получает запрос записать звук с пульта поканально/multitrack или хотя бы master/stereo out для синхронизации с видео. В день события sync_event_recording_fallbacks() может один раз дожать master/stereo у звукача и попросить event-группу взять флешку/накопитель для записи с пульта под монтаж. После события event_materials_archiver.py забирает входящие disk.yandex.* ссылки из orders.db.message_events, привязывает их к активной event-card и сохраняет материалы в наш Yandex Disk archive через LCB_YANDEX_DISK_TOKEN / LCB_EVENT_MATERIALS_YADISK_ROOT. Дедуп идёт через event_ops_state.event_groups[*].media_capture_requests, event_ops_state.event_groups[*].recording_requests и event_ops_state.event_groups[*].material_archives, плюс orders.db.message_events source event_ops_media_capture_organizer_request / event_ops_media_capture_videographer_request / event_ops_recording_request / event_ops_recording_master_followup / event_ops_recording_usb_group_prompt.

confirmedЯвное финальное согласие на эту дату/роль: «ставь за мной», «подтверждаю», либо диалог, где Михаил закрепил дату, условия и финальное go после согласия.

Как реально проходит входящее сообщение
Порядок проверок в unified_dm_responder.handle()
Runtime sequence
1

Listener фиксирует событие

TG inbound идёт через tg_realtime_monitor.py на tg_session_monitor.session; durable suppression проверяется до дорогого context refresh.

2

Dedup и hard routing

handle() сначала проверяет recent handled claim, band member route, broker candidate/client route, musician/aggregator/payment gates и contractor coordination messages. Эти ветки могут завершить поток до LCB writer.

3

Context сборка

agent_context.get_agent_context() — единый read entry для responder: messages, CRM/order, lead-card, event-card, graph/promises. status=Посредник или next_action=BROKER:... выбирает broker event-card через broker_order_context.py; иначе LCB card идёт через lcb_event_context.py.

4

Классификация

Classifier даёт verdict: lead, event organizer, broker, contractor, tech, musician, spam, refusal или unclear. Модельный fallback может меняться, но owner-логика остаётся здесь: verdict выбирает route, а не создаёт второго writer.

5

Writer mode и draft

_suggest_lcb_mode() выбирает mode по последнему сообщению, verdict и CRM. Текст LCB client branch генерируется через lcb_writer.py.

6

Freshness + pre-send

Перед отправкой заново читается tail переписки. Если он изменился, draft не отправляется. Потом идёт единый OutboundReview: duplicate, media, price, payment, contact handoff и AI-review возвращают один result с blocker/decision. Price gate берёт LCB/Noize/outdoor drum totals из price_canon. Media gate блокирует повтор уже отправленного видео-URL, когда клиент просит конкретный/другой ролик; для sax-solo/vendor/named-reference media нельзя подменять конкретный Drive asset или референс общей LCB promo-папкой. Transport gates остаются финальным DeliveryGuard.

7

Send и write-back

После успешной отправки outbound_recorder.record_outbound(namespace="lcb") пишет outbound в memory, обновляет context и promises.

Casting + relay

Подбор подрядчика, проверка маржи, стандартные sax/Noize пакеты из roster/media и relay клиенту. Перед любым broker send broker_casting.cast_order закрывает прошедшие event_date и не допускает, чтобы client_username стал contractor/candidate. Клиентский writer/presend получает thread из orders.db.message_events, не только короткий original_request. Этно-scope в broker сейчас только арабский/восточный; фольклорные/цыганские/казачьи/национальные ансамбли не кастятся. Для drum_show contractor-side route идёт только через broker_vendor_roster.json:drum_show: @vadimnoize / Noize основной, московские backup-подрядчики допускаются только с media-index; клиентский Noize pitch с промо и московским гонораром уходит параллельно с director brief, без ожидания ответа подрядчика.

Правила ownership
Что должна удерживать архитектура

Не плодить writer'ов

Follow-up, listeners и transports только находят событие и доставляют результат. Текст LCB пишет один writer; protected-role gate отсекает musician/performer/vendor/internal контакты до candidate list, а sourcing close-follow-up остаётся на клиентской стороне.

Не делать broker внутри LCB

Broker имеет отдельный state и pipeline. LCB direct lead не превращается в broker order.

Не создавать вторую память

Канальные файлы могут быть cache/export, но смысловая память для writer должна читаться unified layer.

Не обходить agents руками

Если поведение принадлежит agent/process, исправляется владелец, а не выполняется одноразовый workaround. Повторный last_exit!=0 / dashboard FAIL закрывает agent_watchdog.py: bounded kickstart, alert и state, без ручного запуска production scripts.

Budget guard с результатом

GPT/Codex имеет отдельный call-cap; follow-up/write может пройти общий guard, но watchdog блокирует purpose, если серия AI-вызовов не приводит к свежему sent-событию. Realtime broker/private DM path дополнительно использует runtime_loop_guard.py: третий повтор одного handler fingerprint за 5 минут закрывается cooldown до AI/notify.

Payment-семантика через AI

Kirill EDO invoice-loaded решает payment_event_handler: active/reminded/escalated request context → AI verdict → approval draft. Клиентские PDF-платёжки идут через payment_vision → event_payment_balance, сумма/остаток пишутся в event_planning.json. Regex допускается только для механических ID, не как смысловой send/skip gate.
