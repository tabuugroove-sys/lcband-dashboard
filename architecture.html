Как сейчас работает LCB automation

Карта текущей реализации: realtime и scheduled процессы приносят события, state сходится в orders.db и read-model'ы, LCB client text пишет один writer, а broker-переписки уводятся в отдельный broker state до LCB writer.

Мессенджеры

TG / VK / WA / IG

Клиенты, входящие сообщения, исходящие ответы, event/group источники.

Event/group посты

Холодные возможности для LCB или broker, без собственной истории диалога.

Подключения

Постоянные listeners

TG realtime: tg_realtime_monitor.py держит tg_session_monitor.session; VK держит longpoll.

Временные sessions

Send / dry-run / browser walk / export: короткие ручные подключения, не штатные daemon sockets.

Центр

LCB writer

Один production-владелец клиентского текста. Режим выбирается по текущему шагу воронки: intake, sales, contract, production, content, refusal-close, follow-up.

Broker pipeline

Отдельный контур для broker opportunities: подрядчики, media, casting, client relay.

State

orders.db

CRM source of truth: все заказы, статусы, история, event graph, raw message events.

Память переписок

Canonical raw-log в orders.db.message_events; JSONL cache/export по каналам только зеркала.

Выход

Ответ клиенту

Writer пишет, pre-send gates проверяют, transport отправляет в нужный канал.

Обновление state

Входящие и исходящие сообщения возвращаются в orders и память, чтобы следующий шаг видел контекст.

Как реально проходит входящее сообщение
Порядок проверок в unified_dm_responder.handle()
Runtime sequence
1

Listener фиксирует событие

TG inbound идёт через tg_realtime_monitor.py на tg_session_monitor.session; перед writer уже вызывается context refresh.

2

Dedup и hard routing

handle() сначала проверяет recent handled claim, band member route, broker candidate/client route, musician/aggregator/payment gates.

3

Context сборка

lead_context_enricher.get_or_enrich(), resolve_context, lcb_event_context и CRM lookup собирают prompt context.

4

Классификация

Classifier даёт verdict: lead, event organizer, broker, contractor, tech, musician, spam, refusal или unclear. CRM/context могут нормализовать verdict.

5

Writer mode и draft

_suggest_lcb_mode() выбирает mode по последнему сообщению, verdict и CRM: intake/sales/contract/production/event_day/content/complex_request.

6

Freshness + pre-send

Перед отправкой заново читается tail переписки. Если он изменился, draft не отправляется. Потом идёт pre-send review и repair только для repairable blocks.

7

Send и write-back

После успешной отправки outbound_recorder.record_outbound(namespace="lcb") пишет outbound в memory, обновляет context и promises.

Правила ownership
Что должна удерживать архитектура

Не плодить writer'ов

Follow-up, listeners и transports только находят событие и доставляют результат. Текст LCB пишет один writer.

Не делать broker внутри LCB

Broker имеет отдельный state и pipeline. LCB direct lead не превращается в broker order.

Не создавать вторую память

Канальные файлы могут быть cache/export, но смысловая память для writer должна читаться unified layer.

Не обходить agents руками

Если поведение принадлежит agent/process, исправляется владелец, а не выполняется одноразовый workaround.
